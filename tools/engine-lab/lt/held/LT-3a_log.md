### Built
- **Notes past the page's main thread.** A note from a MIDI keyboard went Web MIDI, controller layer, `noteOn`, then a message to the instrument's AudioWorklet, all on the app page's main thread, so a busy moment (drawing, a long task, a project loading) held it back. In the desktop app a small hidden window of the shell (its own renderer process, its own session, nothing else to do) now reads the MIDI inputs and posts each note through a `MessagePort` straight into the played track's AudioWorklet; the voice starts at the next audio block (about 3 ms at 128 frames). Way (1) of the plan: no native module, no change to the desktop build beyond listing the new file.
- **The channel:** the page makes a `MessageChannel`, moves one end into the worklet and posts the other to its own window (`{ ltMidiPort: true }`, the same pattern as the native engine's port); `preload.js` hands it to the shell (`al:lt-port`), the shell hands it to the listening window. No MIDI goes through the shell's main process. A new audio engine (a device change restarts it) makes a new channel; the listening window keeps one per app window and goes away when the last one closes (it never keeps the app open or counts as a window: found and fixed while testing, the app did not quit on Linux and Windows otherwise, and on the Mac the Dock would not open a new window).
- **In the worklet:** lane J's piece goes first in the worklet bundle (`window.LT_WL`, one guarded term in `wlLoad`) and wraps the registration of the pooled voice engine (`al-poly`, lane L's) in a subclass that only listens for `{lt}` messages; the voice DSP and every other message are untouched. The fast path calls the engine's own message format (`n`, `off`), so voices, release and voice stealing are the engine's.
- **What it plays:** notes and the sustain pedal, from plain note inputs only: ports the controller layer treats with its generic profile, not turned off, not halted for a loop, not an IAC, "to Cubase", Network Session or loopMIDI kind of port; a surface (Push, Mackie, Launchpad, APC) turned on is never read. Only reads: nothing is ever sent (no feedback loop); a port sending a flood (over 600 messages a second) is left out for 5 s. Notes learned to a control and MIDI learn waiting for a note are left to lane C's code. The played tracks are `liveTracks()` (armed, or the selected one with the computer keyboard), in this step those with the pooled voice engine (Plant, the basic synths, Wavetable; not Acid, whose slide and accent need the page).
- **No double notes:** the page still gets every note through its own Web MIDI (piano display, recording, meters, lane C's layer) and does not start a voice the worklet started (`voiceOn` wrapped: a note from a port the listening window reports reading, on a track the worklet confirmed). If the shell cannot read MIDI, the page plays as before.
- Nothing runs without a MIDI keyboard and a played track: no channel, no window, no timers (the check runs after a click or a key, like LT-2's). `UI.ltFast=false` turns it off (the Settings row "Fast MIDI notes" comes in LT-3b). `LT_HOOKS.fastNotes()` reports the state for a read-out. In the browser (no shell) nothing changes.
- **For lane C:** `ctlMsg` is wrapped (the way other lanes wrap `noteOn`) only to know which device a note came from; lane C's code is unchanged. `LT_HOOKS.ownsNote` (the plan's name) is not needed: the page asks the fast path in `voiceOn`.

### Measured (build machine, Electron 45 under xvfb, Fractals remake v6, the armed Lead, Linux output clock)
- Note to the voice's first sample on the output clock (`getOutputTimestamp`), median of 8 notes, injected in the listening window as a keyboard would send them; before = the page's own path:
  - **while the page runs a 200 ms long task: before 185.3 ms (168 to 198), after 40.5 ms (37 to 41)**; a first run 182.4 to 39.7 ms.
  - **idle: before 46.5 ms, after 41.2 ms** (first run 44.5 to 36.5). Both include the same output latency of headless Linux (about 30 ms); the injection's own path differs (Playwright into the page, or the shell's main process into the listening window), so idle is "no slower", not a measured gain.
