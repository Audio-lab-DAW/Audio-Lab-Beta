### Found first: device automation was not in exports
Checked with a render: `renderMix` read nothing of `S.pauto`, so an automated filter sweep exported flat (-21.1 dB in every window of a 2 kHz tone swept down by a Low-pass filter and faded by volume automation; live it fell to -65 dB). **Fixed:** `renderMix` now renders `S.pauto`: track volume, pan and the master as curves on the audio parameters (a point every 64 samples), device parameters at every render block (128 samples, 2.7 ms at 48 kHz) where the value moves. Same export now: -21.0, -20.1, -24.3, -47.6, -65.1 dB at 0.2, 1, 2, 3 and 3.8 s. Live playback sets automation from the screen every 33 ms and smooths it, so it follows the exact export curve about 80 ms later (median difference 0.06 dB once that lag is taken out; measured). Not yet rendered in exports: Venom's own settings (`i:`), device controls of instruments (`c:`) and macros (`x:`); see Left. Parameters that Vector Map moves are left to Vector Map's own export. Several features stop an offline render at the same moment (Vector Map, the progress line, automation): `mxSuspWrap` merges them, so none of them is refused.

### Built
- **X5, one plan for every path** (`mxSolve`, behind the unchanged `pdcMap(sr)`, now `pdcMap(sr,live)`): each track's latency, its output (master, group, return or another track), its sends before and after the fader, and every Ducker trigger (with the latency of the devices before the Ducker). The longest path to the master sets the target; every link gets the delay that makes its sound arrive with the others. Tracks keep today's delay after their effects (`N.pdc`), groups and returns keep none of their own, and only a link that needs more gets a delay node of its own (an output, a send, a trigger). A trigger that would arrive late (the kick has a compressor) makes the ducked track wait at its input instead. A track that receives another track's output and has clips of its own gets the same input delay for its clips. An empty group or return no longer holds the others back. `UI.pdc=false` still turns everything off. Export builds the same delays from the same plan.
- **Latency changes while playing fade** (8 ms down, 8 ms up, set a little ahead of the audio thread) on the paths that move, instead of jumping; nothing runs while nothing changes.
- **Lane J's played-track hook**: `pdcMap(sr,true)` asks `LT_HOOKS.pdcLive()` (when lane J has made it) which tracks are played live; those get no delay while the rest stays compensated. Exports never ask it.
- **X6, subtle and in few places**: a small grey read-out next to the name in the track's first device (the channel strip on the left), only when the track's own devices add latency, for example "3.0 ms". Tooltip: "The devices on Resample delay its sound by 3.0 ms (132 samples). AudioLab delays the other tracks, sends and returns to match, so everything stays in time. Longest path in the song: 5.0 ms (Glue, Limiter)." With compensation off it says the track plays this much late. It updates on changes only.
- `fxLat`: the browser's Compressor (and OTT) delay by 6 ms cut to whole samples: 264 at 44.1 kHz, not 265 (measured with an impulse). 48 kHz unchanged (288).
- Hooks `window.MX_HOOKS`: `lat(t)`, `devLat(t,f)` → `{smp, ms, text}` (for lane I's device hover), `pathLat()` → the longest path, its track and the device on it with the most latency (lane C's routing map), `pdcPlan(sr)` (every delay of the plan); `links()` now carries each link's added delay in ms.
