AudioLab extensions, round 1

Your question: can people customise the interface and build their own devices, somewhere inside the software, maybe through the chat box. Short answer: yes, in five small stages, and four of them already run on this page. Try each prototype, then choose at the bottom and paste the line.

Prototype 2 · Stage 2

A device made from a description file

The file lists the knobs (range, unit, start value), the blocks that make the sound and how they are wired, the display and which knobs sit in the dock. Change a range, rename a knob, add a block: the device rebuilds. The sound comes from ordinary Web Audio nodes here; in the app the blocks would be AudioLab's own effects.

my-device.audiolabdevice

Drag a knob up or down; double-click resets it. The round button at the top left switches the device off. Block types in this round: gain, delay, filter, drive, pan, comp, reverb, lfo.

Prototype 3 · Stage 3

A tiny script device with a CPU meter

For sounds the blocks cannot make. The script runs once per sample inside an audio worklet. The language is deliberately small: numbers, maths, if, a fixed-count loop and a delay memory. It has no way to name anything outside itself and it cannot loop for ever, so a script can sound bad but cannot freeze the audio. Before a script goes live it is test-run off the audio thread and its cost is measured.

Safety rules that hold in every stage

  1. User files never get the app's own powers: no file access, no network, no access to the project, no Node. Themes and descriptions are read as data. Scripts are compiled by AudioLab into code that can only touch its own numbers.
  2. A host-owned safety stage sits after every user device: broken numbers become silence, the level is limited, and a device that blasts is muted. It cannot be removed by the file.
  3. No script can loop for ever. Loops have a fixed count and the worst-case work per sample is worked out before it runs.
  4. Every device is test-run off the audio thread first. Too heavy or too loud: it does not go live.
  5. A watchdog in the audio thread bypasses a device that starts to overrun, and says so.
  6. Imported files are size-capped and checked field by field; unknown fields are ignored, never run.
