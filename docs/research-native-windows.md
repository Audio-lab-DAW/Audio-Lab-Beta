## 0. The short version

1. **Windows has no single "Core Audio".** A DAW on Windows needs two device paths, not one: **WASAPI** (Microsoft's own, every device, shared or exclusive) and **ASIO** (Steinberg's, low latency through the interface maker's driver). Every serious DAW except Ableton offers both; Cubase offers only ASIO; FL Studio and Steinberg wrap WASAPI inside their own ASIO driver. AudioLab should offer both, WASAPI exclusive first because it serves the user's DACs bit-perfect and needs no licence.
2. **ASIO in a closed-source app needs Steinberg's licence agreement.** Since October 2025 the ASIO SDK is GPLv3 or a free proprietary agreement. Steinberg's own FAQ (21 October 2026) says the agreement is needed even if you do not use their SDK files, as soon as you talk to ASIO drivers. It costs nothing and individuals can sign, but replies have taken **five weeks to three months** in 2026. **The single most useful thing to do now is to send the signed agreement**, because nothing can be shipped with ASIO until it comes back.
3. **USB class-compliant devices are slow on Windows today.** Microsoft's own driver for USB Audio 2.0 (`usbaudio2.sys`) has no ASIO and in Microsoft's words "isn't great for music creation" (about 10 ms). Microsoft, Yamaha and Qualcomm are building a new in-box low-latency USB driver with ASIO built in; on 27 November 2026 it is **still not publicly released**. So on Windows the Zoom AMS-24 needs Zoom's own driver for low latency, and the Gryphon will do best on iFi's driver (ASIO, native DSD) or on WASAPI exclusive.
4. **Windows quietly slows a DAW down unless the DAW says no.** On Intel hybrid CPUs Windows moves threads of a covered or background window to the slow E-cores, relaxes the timer, and limits each process to 32 MMCSS (real-time) threads. Steinberg has a help article for exactly this dropout. The engine must opt out of power throttling, keep its timer resolution, pin audio work to P-cores with CPU Sets, and keep its real-time thread count small. All of this is a few dozen lines and is the biggest stability gain per hour on Windows.
5. **Plug-in stability on Windows** is about more than crashes: plug-ins change the floating-point state, call COM on the host's thread, block in activation, need a message pump, are DPI-unaware, are slowed by Defender, and crash on unload. Every one has a known host-side defence (section 5). Out-of-process hosting costs real CPU at small buffers (Ardour's estimate: several ms per block if every plug-in runs alone), so the model to copy is REAPER's: in the engine by default, "run apart" per plug-in, grouped.
6. **Electron at 240 Hz on Windows has a trap:** Chromium waits for the vertical blank of the **primary** monitor. If the user's 240 Hz screen is not the primary one, the interface may run at the other screen's rate. This needs a check on the user's PC, and is a strong argument for native drawing (Direct3D flip model or Skia) for the meters, waveforms and the glass later.
7. **Distribution:** the Windows app is unsigned today, so every download shows "Windows protected your PC", Smart App Control can block it, and the updater cannot check who made an update. Azure Artifact Signing (formerly Trusted Signing) is US$9.99 a month, but **individuals must be in the US or Canada**; organisations in the EU, UK and a few other countries qualify. Keep NSIS; MSIX cannot install plug-ins into the shared VST3 folder.
8. **Testing on Windows CI is possible but not with sound out of the box.** GitHub's `windows-latest` (Server 2025) has a desktop session but no audio device. Mozilla's audio library CI installs the VB-CABLE virtual device on the runner; that is the way to get a loop-back device, with a licence note.

Proposed tasks are in section 11 (named W1 to W18, each one cloud task of 1 to 3 hours). The changes the native plan needs for Windows are in section 12.

## 1. The Windows audio stack

### 1.1 The layers

| Path | What it is | Latency you can expect | Bit-perfect? | Licence |
|---|---|---|---|---|
| **WASAPI shared** | Windows mixes every app in 32-bit float, at the format the user picked in the Sound panel | default engine period 10 ms; the engine adds 1.3 ms on output ([Microsoft, low latency audio](https://learn.microsoft.com/en-sg/WINDOWS-HARDWARE/DRIVERS/audio/low-latency-audio)) | no (resampler, limiter, dither, other apps) | none |
| **WASAPI shared, low-latency (IAudioClient3)** | the same mixer at a smaller period, if the driver allows it | 2.7 to 10 ms; ~10 ms on most USB devices **(guess)** | no | none |
| **WASAPI exclusive** | one app owns the device; data goes straight to the driver | down to the device's minimum period (often 3 ms or less on good drivers) | **yes** | none |
| **ASIO** | the interface maker's own driver, a separate path past Windows | 3.7 to 8 ms round trip at 64 frames on good interfaces (table in 1.6) | yes | Steinberg agreement (section 2) |
| **WDM Kernel Streaming** | the layer under WASAPI, used directly | like exclusive | yes | none; fragile, not worth building (1.5) |
| MME, DirectSound | old APIs on top of WASAPI | high | no | none; not needed |

### 1.2 WASAPI shared mode, and why it is not clean

- Windows mixes in 32-bit float at its own "mix format" and converts every stream to it: resample if needed, convert to float, mix, dither if the device is 16-bit, convert to integer. This happens even when only one app plays ([Microsoft, device formats](https://learn.microsoft.com/en-ie/Windows/Win32/coreaudio/device-formats); [The Well-Tempered Computer](https://thewelltemperedcomputer.com/SW/Windows/SRC.htm)).
- **A limiter** (`CAudioLimiter`) sits at the end of the float path, just before the conversion to integer ([Microsoft archive, audio fidelity](https://learn.microsoft.com/nl-nl/archive/blogs/audiofool/audio-fidelity-clipping); [WinSoftVol](https://github.com/dechamps/WinSoftVol)).
- **The resampler is poor by default.** Measurements of Windows 10's shared path at 44.1 to 96 kHz showed heavy aliasing near 20 kHz and an impulse consistent with linear interpolation ([Archimago, 2015](https://archimago.blogspot.com/2015/11/measurements-windows-10-audio-stack.html)). A better one can be asked for with `AUDCLNT_STREAMFLAGS_SRC_DEFAULT_QUALITY` ([stream flags](https://learn.microsoft.com/en-us/windows/desktop/CoreAudio/audclnt-streamflags-xxx-constants)); no measurement of it was found. Rule for AudioLab: never let Windows resample; do it ourselves or open the device at the project's rate.
- **System effects** (APOs, the maker's "enhancements") add processing and latency; `AUDCLNT_STREAMOPTIONS_RAW` bypasses them if the device says it can ([Microsoft, low latency audio](https://learn.microsoft.com/en-sg/WINDOWS-HARDWARE/DRIVERS/audio/low-latency-audio)).
- **The shared format cannot be set by an app** through a documented API; only the user can, in the Sound panel. It can be read (`PKEY_AudioEngine_DeviceFormat`, [Microsoft](https://learn.microsoft.com/en-us/windows/win32/coreaudio/pkey-audioengine-deviceformat)). An undocumented interface (`IPolicyConfig`) is used by tools like Sunshine ([PolicyConfig.h](https://docs.lizardbyte.dev/projects/sunshine/master/PolicyConfig_8h.html)); its ID has changed between Windows builds **(guess)**, so at most an optional "set it for me" button with a fallback to opening the Sound panel.
- This is what the Electron app uses today, so the current Windows AudioLab is never bit-perfect and always passes the limiter. That was already noted in `settings-research-audiophile.md`.

### 1.3 IAudioClient3: low-latency shared mode

- `GetSharedModeEnginePeriod` returns default, fundamental, minimum and maximum periods; `InitializeSharedAudioStream` opens a stream at a multiple of the fundamental. Microsoft's example: 448 frames default, 48 minimum at 44.1 kHz ([IAudioClient3](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudioclient3-initializesharedaudiostream)).
- It works only if the driver declares small packet sizes. The in-box HD Audio driver allows 128 to 480 frames (2.66 to 10 ms at 48 kHz) ([Microsoft](https://learn.microsoft.com/en-sg/WINDOWS-HARDWARE/DRIVERS/audio/low-latency-audio)). Other drivers report min = max = 480, which JUCE users see as "only 480 samples" ([JUCE forum](https://forum.juce.com/t/why-is-the-audio-buffer-size-only-480-samples-in-windows-audio-low-latency-mode/49408)).
- When one app asks for a small period, every app on that device is switched to it until that app exits (same Microsoft page).
- **For AudioLab:** worth offering as "Shared, low latency" for laptop speakers and headphones on the built-in audio, where it brings 10 ms down to about 3 ms with no exclusive lock. Not a path for USB DACs.

### 1.4 WASAPI exclusive: the bit-perfect path

- Event-driven exclusive: read the minimum period with `GetDevicePeriod`, call `Initialize(EXCLUSIVE, EVENTCALLBACK, d, d, format)`; buffer duration must equal period ([IAudioClient::Initialize](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudioclient-initialize)).
- **The alignment dance:** many devices answer `AUDCLNT_E_BUFFER_SIZE_NOT_ALIGNED`. The fix is documented: read the aligned size with `GetBufferSize`, release the client, compute the period from it, activate a new client, initialise again (same page). A failed client cannot be reused. This is the most common bug in hand-written WASAPI code **(guess)**.
- **Format negotiation:** in exclusive mode the format must be one the hardware takes exactly. Some drivers accept stereo as `WAVEFORMATEX` and refuse `WAVEFORMATEXTENSIBLE`, so try both ([device formats](https://learn.microsoft.com/en-ie/Windows/Win32/coreaudio/device-formats)). The order to try **(guess, standard practice)**: 32-bit integer; 24 valid bits in 32; packed 24; 16; float. The USB class driver accepts 1 to 4 bytes per sample, 8 to 32 bits ([USB Audio 2.0 drivers](https://learn.microsoft.com/windows-hardware/drivers/audio/usb-2-0-audio-drivers)).
- **Sample-rate switching:** opening exclusive at the file's or project's rate switches the device's clock; this is how foobar2000, JRiver and Roon switch rates per track. On a few old sound cards exclusive does not switch the master clock and only the maker's ASIO does ([JRiver wiki](https://wiki.jriver.com/index.php/Output_Mode)).
- **Refusals the app must explain in words:** `AUDCLNT_E_DEVICE_IN_USE` (someone else holds it), `AUDCLNT_E_EXCLUSIVE_MODE_NOT_ALLOWED` (the user unticked "Allow applications to take exclusive control" in the Sound panel). When exclusive pre-empts other apps, they receive `DisconnectReasonExclusiveModeOverride` ([exclusive-mode streams](https://learn.microsoft.com/en-ie/Windows/Win32/coreaudio/exclusive-mode-streams)).
- **Volume in exclusive mode:** session volume does nothing; only the endpoint volume (`IAudioEndpointVolume`) works (same page). That is exactly the synced device volume the user wants (1.7).
- WASAPI gives its own threads the MMCSS "Pro Audio" class below 10 ms; the app's thread should join it too (same page).

### 1.5 Kernel Streaming, MME, DirectSound

All of them sit on the same kernel layer; KMixer is gone since Vista ([PortAudio](https://github.com/PortAudio/portaudio/wiki/Win32AudioBackgroundInfo)). Kernel Streaming fails if any other app has the device open, often fails on default devices, and offers only native formats ([FlexASIO FAQ](https://github.com/dechamps/FlexASIO/blob/master/FAQ.md)). WASAPI exclusive gives the same clean path with a supported API. **Do not build KS, MME or DirectSound.**

### 1.6 USB devices: the in-box driver, makers' drivers, and Microsoft's new one

- **`usbaudio2.sys`**, in Windows since 10 version 1703, written by Thesycon for Microsoft: asynchronous, synchronous and adaptive modes, one clock source, 8 channels in shared mode, no MIDI, **no ASIO** ([Microsoft](https://learn.microsoft.com/windows-hardware/drivers/audio/usb-2-0-audio-drivers); [XMOS](https://www.xmos.com/?p=37811)). Microsoft says the native stack "typically" sits "around 10 ms" while ASIO drivers reach single digits ([Making music on Windows](https://devblogs.microsoft.com/windows-music-dev/making-music-on-windows/)). No published side-by-side round-trip figures were found.
- **Thesycon's paid driver** is what many USB interfaces and DACs ship under their own name: ASIO 2.3.1, several ASIO apps at once plus Windows sound, native DSD up to DSD1024 ([Thesycon](https://thesycon.de/eng/usb_audiodriver.shtml)). XMOS sends its customers there ([XMOS](https://www.xmos.com/?p=37811)).
- **Measured round trip on Windows ASIO at 48 kHz** ([JackTrip community table, Dec 2024](https://community.jacktrip.org/t/audio-interface-latency-measurements/1118)):

| Interface | 32 frames | 64 | 128 |
|---|---|---|---|
| RME Babyface Pro FS | n/a | 3.8 ms | 6.5 ms |
| Behringer UMC202HD | 3.7 | 4.4 | 6.7 |
| PreSonus AudioBox USB 96 | 3.8 | 4.4 | 6.8 |
| NI Komplete Audio 6 MkII | 4.5 | 5.2 | 8.5 |
| Focusrite 2i2 Gen 3 | 5.5 | 7.8 | 14.5 |
| Steinberg UR22 | 5.4 | 8.7 | 13.4 |

  Sound On Sound found 3.6 to 12.2 ms across PC interfaces at a nominal 64 frames: drivers add hidden safety buffers they do not always report ([SOS](https://www.soundonsound.com/techniques/round-trip-latency-rtl-j-scope-oscilloscope)). So the buffer number in a DAW's settings says little; **the app should measure** (task W9).
- **Microsoft's new in-box low-latency USB driver with ASIO.** Built on ACX by Microsoft with Yamaha and Qualcomm; Arm first, x64 too; Windows sound and ASIO on the same device at the same time; no device aggregation in 1.0; source under MIT at [microsoft/low-latency-audio](https://github.com/microsoft/low-latency-audio) ([Fall 2025 update](https://devblogs.microsoft.com/windows-music-dev/fall-2025-windows-musician-technology-and-arm64-update/); [SOS, "ASIO goes native"](https://www.soundonsound.com/music-business/asio-goes-native)). The only figure: about 4 ms round trip on early builds, reported by Qualcomm. **Status on 27 Nov 2026: the repository still says there is no public release.** Microsoft said in June 2026 an optional preview would come "this fall" ([KVR](https://www.kvraudio.com/forum/viewtopic.php?p=9259472)); no Insider build was found. When it ships, every class-compliant device gets an ASIO path with no maker's driver, so AudioLab's ASIO path pays off twice.

### 1.7 Device volume, plugging, and changes from outside

This is the Windows half of the synced device volume the user asked for (the Mac half works in test app 0.2).

- **`IAudioEndpointVolume`**: get and set the level (scalar or dB), mute, and `QueryHardwareSupport`, which says whether the device has hardware volume, mute or meter; Windows substitutes software volume for what the hardware lacks ([Microsoft](https://learn.microsoft.com/en-us/windows/win32/api/endpointvolume/nf-endpointvolume-iaudioendpointvolume-queryhardwaresupport)). Changes from anywhere (the tray, the keyboard, another app) arrive through `IAudioEndpointVolumeCallback::OnNotify`. The USB class driver maps a USB Audio 2.0 volume control to hardware ([USB Audio 2.0 drivers](https://learn.microsoft.com/windows-hardware/drivers/audio/usb-2-0-audio-drivers)).
- **Important for the app's wording:** on Windows, "the device has no volume" is rarer than on the Mac, because Windows fakes it in software. The app must show which one it is: "the DAC's own volume" when `QueryHardwareSupport` says hardware, "Windows volume (in software, before the DAC)" otherwise. In exclusive mode software volume does not apply, so a device without hardware volume simply has none there **(guess, follows from 1.4)**.
- **`IMMNotificationClient`**: device added, removed, state changed, default changed, property changed. Callbacks must not block, must not register or unregister, must not drop the last reference to a device ([Microsoft](https://learn.microsoft.com/en-us/windows/win32/api/mmdeviceapi/nn-mmdeviceapi-immnotificationclient)).
- **Device lost:** calls return `AUDCLNT_E_DEVICE_INVALIDATED` after unplug, disable, a format change by the user, or being pushed out by an exclusive app. Windows does not recover for you: release everything, try the same device id again, else fall back to the default and say so ([Microsoft, recovering](https://learn.microsoft.com/en-ie/Windows/Win32/coreaudio/recovering-from-an-invalid-device-error); [Larry Osterman](https://learn.microsoft.com/en-us/archive/blogs/larryosterman/what-happens-when-audio-rendering-fails)). The same behaviour the Mac test app showed when the Gryphon was pulled out.
- **A Windows bug to know:** on 24H2 an external USB DAC could jump to 100 % volume after sleep or unplug (fixed by Microsoft) ([Microsoft](https://support.microsoft.com/en-US/servicing/os/windows/2024/11/windows-gaming-system-external-usb-audio-volume-increases-to-100-percent)). For a DAC at headphone level that is dangerous: the engine should **read the volume back after every device return and after resume from sleep**, and apply AudioLab's safe-volume rule if it jumped.

### 1.8 Several devices at once

Windows has no aggregate device like the Mac's ([Fall 2025 update](https://devblogs.microsoft.com/windows-music-dev/fall-2025-windows-musician-technology-and-arm64-update/)). ASIO is one driver for in and out. Two devices have two clocks, and the only fix is an adaptive resampler that follows the drift ([FlexASIO FAQ](https://github.com/dechamps/FlexASIO/blob/master/FAQ.md)). The engine already needs that resampler for stage N2 on the Mac (`native-mac-build.md`); the same code serves "input from the Zoom, output to the Gryphon" on both systems.

## 2. ASIO: licence, how it works, wrappers

### 2.1 The licence, today

- Since October 2025: **GPLv3, or the "Steinberg ASIO SDK Licensing Agreement"** ([heise](https://heise.de/-10963451); [Libre Arts](https://librearts.org/2025/11/steinberg-relicenses-vst3-and-asio/)). AudioLab is `UNLICENSED` (closed), so GPLv3 is not an option.
- **Steinberg's FAQ of 21 October 2026** ([forum, pinned](https://forums.steinberg.net/t/asio-sdk-proprietary-license-frequently-asked-questions/1044024)):
  - a closed host needs the agreement if it "uses the ASIO SDK **or interface technology** to talk to ASIO drivers". So writing our own header from public descriptions does not avoid it, in Steinberg's view; one developer using NAudio without the SDK read this and signed ([forum](https://forums.steinberg.net/t/asio-licensing-question-for-a-commercial-application-using-naudio/1042368));
  - **free**: no application, renewal, per-product, per-copy or revenue fee;
  - **individuals may sign**: legal name in both company and representative fields, title "Individual Developer";
  - **how**: email the signed PDF (in the SDK zip) to `sdklicenseagreements@steinberg.de`; Steinberg countersigns;
  - **before countersignature** you may develop and test internally, but not distribute anything, not even a free beta;
  - one agreement covers all your products; frameworks like JUCE or PortAudio are fine; the SDK itself must not be passed on (so `asio.h` must not be in this public repository **(guess, follows)**);
  - the line "ASIO is a registered trademark of Steinberg Media Technologies GmbH." and only the official "ASIO Compatible" logo.
- **Waiting times reported in 2026:** sent 25 July, no reply by 22 October; sent 9 September, no reply after five weeks (old address); sent 8 November to the new address, automatic receipt only by 16 November ([forum](https://forums.steinberg.net/t/proprietary-asio-sdk-license-agreement-no-response-after-5-weeks-odemi-daw/1043608); [ASIO category](https://forums.steinberg.net/c/developer/asio/104)).
- **SDK version:** 2.3.4 is the newest found. No official Steinberg GitHub repository exists. Two host-side bugs in the SDK's helper files were reported in 2026 (a mismatched `delete[]` in `asiolist.cpp`, fixed buffer limits in `asiodrivers.cpp`) (forum, and the [Codeberg copy](https://codeberg.org/rubiefawn/asiosdk) has the fix). Our own small loader is better than the SDK's helper files **(guess)**.
- Not legal advice. The agreement text (version 2.0.5, in the SDK zip) should be read before signing.

**Recommendation: the user signs and sends the agreement now** (task W0, about 15 minutes of the user's time). The repository is public, so the SDK files must live outside it: the CI fetches them from Steinberg's download at build time, as the VST3 workflow already does for its SDK.

### 2.2 How a host talks to ASIO

From the SDK (`common/asio.h`, `host/pc/asiolist.cpp`; read through a [copy](https://github.com/jcelerier/asio-2)):

- **Finding drivers:** subkeys of `HKLM\SOFTWARE\ASIO`, each with `CLSID` and `Description`; the DLL path is under `HKCR\CLSID\{clsid}\InprocServer32`; create with `CoCreateInstance(clsid, …, clsid, …)` (the class id doubles as interface id: ASIO is COM-like, not proper COM). A 64-bit host sees only 64-bit drivers.
- **One driver per process** in the SDK's design: one global driver pointer, callbacks without a context pointer.
- **The callback** `bufferSwitchTimeInfo` runs on the **driver's** thread, which the driver puts in MMCSS "Pro Audio"; the host must not change it (ASIO 2.3, cited in the [Steinberg forum](https://forums.steinberg.net/t/make-mmcss-registration-optional-in-asio-host-applications/201817)).
- **`ASIOOutputReady()`** after filling the buffers saves one block of latency where the driver supports it.
- **Messages:** `kAsioResetRequest` (close and reopen: the driver's panel changed the buffer or rate), `kAsioResyncRequest`, `kAsioLatenciesChanged`, `kAsioBufferSizeChange` (documented as not supported; treat as reset), `kAsioOverload` (unreliable; RME dropped it, [RME forum](https://forum.rme-audio.de/viewtopic.php?id=26601)).
- **Never stop or close the driver from inside its own callback.** RtAudio crashed an SSL 2+ driver that way and moved the reset to another thread ([RtAudio #235](https://github.com/thestk/rtaudio/issues/235)). Rule: post every driver message to a control thread, with a time limit on `ASIOStop` and `ASIOExit`, because drivers hang.
- **Sample types:** on Windows mostly `Int32LSB` and `Float32LSB`, plus 16, 24 and padded types; DSD through `ASIOFuture(kAsioSetIoFormat, kASIODSDFormat)` before buffers are created.
- **Latency:** `ASIOGetLatencies` (input and output) plus `kAsioGetInternalBufferSamples` where the driver answers it; read again after `kAsioLatenciesChanged`.
- **The driver's panel:** `ASIOControlPanel()` opens the maker's window; changes come back as a reset request.

### 2.3 Wrappers and generic drivers

- **ASIO4ALL** 2.22 (23 July 2026), free for users, but "commercial exploitation (resale/bundling…)" is restricted: **do not bundle it**. It uses Kernel Streaming, so other apps go silent "by design", and it can only guess latencies ([asio4all.org](https://asio4all.org/about/); [troubleshooting](https://asio4all.org/troubleshooting/)).
- **FlexASIO**: MIT, on PortAudio, can run WASAPI shared (several apps at once) or exclusive; default buffer 20 ms ([FlexASIO](https://github.com/dechamps/FlexASIO)).
- **Steinberg's built-in ASIO driver**: supported only with Steinberg's own software.
- **For AudioLab:** none of these is needed, because the engine speaks WASAPI itself. Users who only have ASIO4ALL get told that "WASAPI exclusive" in AudioLab does the same thing better.

## 3. Real-time performance on Windows

### 3.1 MMCSS ("Pro Audio")

- The Pro Audio task runs threads at priorities 23 to 26, "below only certain system-level tasks" ([Microsoft, MMCSS](https://learn.microsoft.com/en-us/windows/win32/procthread/multimedia-class-scheduler-service)). A thread that uses up its share (by default up to 8 of every 10 ms) drops to priority 1 to 7 ([Russinovich](https://learn.microsoft.com/en-us/archive/blogs/markrussinovich/vista-multimedia-playback-and-network-throughput)).
- **That drop is a real cause of clicks** at tiny buffers: Antelope measured the DAW thread losing its priority below 64 frames at 192 kHz ([Steinberg forum](https://forums.steinberg.net/t/make-mmcss-registration-optional-in-asio-host-applications/201817); [Antelope](https://support.antelopeaudio.com/en/support/solutions/articles/42000045319-about-scheduling-priorities-and-multimedia-class-scheduler-service-mmcss-)). REAPER makes MMCSS optional for this reason.
- **32 MMCSS threads per process**, about 4 already used: Cubase before version 10 lost real-time priority on machines with more than 14 logical cores ([Steinberg](https://www.steinberg.help/r/windows-10-audio-dropouts-on-multi-core-cpu-setups); [Microsoft Q&A](https://learn.microsoft.com/en-us/answers/questions/2769483/windows-10-limits-max-number-32-of-threads-with)).
- Microsoft's preferred way for WASAPI is the Real-Time Work Queue (`RtwqLockSharedWorkQueue(L"ProAudio")`) ([Microsoft](https://learn.microsoft.com/en-sg/WINDOWS-HARDWARE/DRIVERS/audio/low-latency-audio)). Windows has no equivalent of the Mac's audio workgroups ([JUCE forum](https://forum.juce.com/t/audio-workgroups-equivalent-on-windows/58626)).

### 3.2 How DAWs use many cores

- **Cubase ASIO-Guard:** two paths. Armed and monitored tracks run at the device buffer; everything else is rendered ahead into a larger buffer ([Steinberg](https://www.steinberg.help/r/details-on-asio-guard-in-cubase-and-nuendo)).
- **Studio One:** device block size for monitored inputs, a larger process block ("dropout protection") for the rest ([PreSonus](https://support.presonus.com/hc/en-us/articles/360045431251-Studio-One-5-Audio-Dropout-Protection-and-Low-Latency-Monitoring-FAQ)).
- **REAPER:** "anticipative FX processing" renders unarmed tracks ahead (about 200 ms reported) (forum; [user guide](https://dlz.reaper.fm/userguide/ReaperUserGuide720c.pdf)).
- **Ableton:** a serial chain cannot be split across cores; audio runs on performance cores only ([Ableton](https://help.ableton.com/hc/en-us/articles/209067649)).
- **Measured (DAWbench, late 2025, 9950X, Threadripper 9750WX, Core Ultra 9 285K):** REAPER ran about 85 more plug-ins than Cubase on the 285K; going from 32 to 64 threads gave REAPER 1 to 8 % and the others almost nothing: no DAW scales well past about 32 threads once busses are used ([DAWbench](https://dawbench.substack.com/p/windows-and-daws-822)).
- **Waking workers** is the hard part; Tracktion found a short spin then a wait on a semaphore best, and says steady timing matters more than average CPU ([ADC 2020 talk thread](https://forum.juce.com/t/adc-tracktion-graph-talk/43052)).
- **For AudioLab:** the engine should be built two-path from the start (live set at the device buffer, the rest rendered ahead). This matters on both systems; on Windows it is also how to stay under the MMCSS thread limit.

### 3.3 Power throttling, the hidden enemy

- Windows 11 gives each process a quality-of-service level: High when focused **or audible**; Medium when visible; **Low when minimised or covered**, which on hybrid CPUs means E-cores and lower clocks ([Microsoft QoS](https://github.com/MicrosoftDocs/win32/blob/docs/desktop-src/ProcThread/quality-of-service.md)).
- An ASIO or exclusive stream goes past the Windows mixer, so Windows may not count the DAW as "audible" **(guess)**. Steinberg's own help article: on Intel hybrid CPUs, Cubase in the background drops out because its render-ahead threads move to E-cores; the fix given is `powercfg /powerthrottling disable /path "<exe>"` ([Steinberg](https://www.steinberg.help/r/windows-dropouts-on-intel-hybrid-architecture-cpus-with-cubase/nuendo-running-in-background)).
- **The engine can do it itself, without admin:** `SetProcessInformation(ProcessPowerThrottling)` with the execution-speed bit in the mask and 0 in the state; `SetThreadInformation(ThreadPowerThrottling)` per thread ([Microsoft](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-setprocessinformation)). Same call, other bit, for the timer (3.4).
- Task Manager's "Efficiency mode" puts a process on EcoQoS and low priority ([Microsoft](https://devblogs.microsoft.com/performance-diagnostics/reduce-process-interference-with-task-manager-efficiency-mode/)); the engine should detect and report it.
- Power plans: Steinberg recommends High Performance and turning off USB selective suspend ([Steinberg](https://www.steinberg.help/r/windows-how-to-set-up-and-optimize-a-digital-audio-workstation)). The app should **report** the active plan and USB suspend, not change them silently.

### 3.4 Timer resolution

Since Windows 10 2004, `timeBeginPeriod` affects only the calling process; on Windows 11 a minimised, covered or inaudible window loses the high resolution unless the process opts out (`PROCESS_POWER_THROTTLING_IGNORE_TIMER_RESOLUTION` in the mask, off in the state) ([Microsoft](https://learn.microsoft.com/en-us/windows/win32/api/timeapi/nf-timeapi-timebeginperiod)). High-resolution waitable timers exist since Windows 10 1803 ([Microsoft](https://learn.microsoft.com/windows/win32/api/synchapi/nf-synchapi-createwaitabletimerexw)). The audio itself is driven by the device (ASIO callback, WASAPI event), so timers only matter for housekeeping and render-ahead.

### 3.5 Hybrid Intel, AMD, Arm

- **Intel 12th gen and later:** read cores with `GetSystemCpuSetInformation` (higher `EfficiencyClass` = P-core); use soft **CPU Sets** (`SetThreadSelectedCpuSets`, or the `…Masks` version across processor groups), not hard affinity, which makes Windows ignore Thread Director ([Intel](https://www.intel.com/content/www/us/en/developer/articles/guide/12th-gen-intel-core-processor-gamedev-guide.html)). Users still report real-time peaks on hybrid Intel in 2026 with no root cause found ([Steinberg forum](https://forums.steinberg.net/t/realtime-peaks-and-crackles-during-monitoring-on-modern-intel-systems/1033286)).
- **AMD with two chiplets (CCDs), X3D:** the V-Cache driver parks one chiplet when it detects a game; a DAW is not a game, so its threads spread across both, and a hand-off between chiplets inside one block costs time (forum; [hwbusters](https://hwbusters.com/cpu/amd-ryzen-9-7950x3d-core-parking-problem-solution/)). Keep one chain's work on one chiplet, grouped by `LastLevelCacheIndex` **(guess)**.
- **More than 64 logical processors:** since Windows 11 threads may span processor groups; CPU Sets work across them ([Microsoft](https://learn.microsoft.com/windows/desktop/ProcThread/processor-groups)).
- **Windows on Arm (Snapdragon X):** Cubase, REAPER, Bitwig and Studio One are native; FL Studio and Ableton are not yet ([Sweetwater, 25 Nov 2026](https://www.sweetwater.com/sweetcare/articles/windows-on-arm-compatibility-guide/)). A host built as **Arm64EC** can load x64 plug-ins in its own process under emulation ([Microsoft](https://devblogs.microsoft.com/windows-music-dev/load-x64-plug-ins-like-vsts-from-your-arm-code-using-arm64ec/)). iLok-protected plug-ins mostly do not run on Arm as of July 2026 ([Production Expert](https://www.production-expert.com/production-expert-1/windows-on-arm-for-your-studio-what-audio-pros-need-to-know)). Low priority for AudioLab; x64 first.

### 3.6 DPC latency: detect it and tell the user

- A DPC (a driver's deferred work) blocks every thread on its core; Microsoft's guideline is at most 100 µs per call ([Microsoft](https://learn.microsoft.com/en-sg/WINDOWS-HARDWARE/DRIVERS/kernel/guidelines-for-writing-dpc-routines)). Usual culprits (forum): Wi-Fi, the graphics driver, ACPI, USB, storage.
- LatencyMon reads the kernel's event trace and needs admin and a helper driver ([Resplendence](https://www.resplendence.com/latencymon_technical)). Only one kernel trace session exists system-wide.
- **What AudioLab can measure without admin (guess, standard technique):** in every audio callback, (1) how late it woke compared with the expected time, (2) wall time against the thread's own CPU cycles (`QueryThreadCycleTime`): much wall time with few cycles means the thread was interrupted or pre-empted, (3) page faults per block, (4) which core it ran on and whether it is an E-core. Shown as a "System check" panel: worst lateness, how often the deadline was missed, and a plain sentence ("Something on this PC stops audio for up to 1.8 ms; this is usually a driver. Try turning off Wi-Fi to see if it goes away."). An optional admin mode could name the driver through the kernel trace, later.

### 3.7 Floating point, memory, files

- **Denormals:** set flush-to-zero and denormals-are-zero (MXCSR) on every audio and worker thread, and **save and restore the floating-point state around every plug-in call**, because plug-ins change it and do not always put it back ([Dplug's handling](https://dplug.dpldocs.dlang.org/source/dplug.core.fpcontrol.d.html)).
- **Memory:** allocate and touch every real-time buffer before playing; `VirtualLock` after raising the working set ([Microsoft](https://learn.microsoft.com/en-us/windows/desktop/api/memoryapi/nf-memoryapi-virtuallock)). No file I/O on the audio thread.

### 3.8 Known Windows 11 trouble

24H2 brought reports of dropouts and audio drivers needing reinstall ([Steinberg forum](https://forums.steinberg.net/t/windows-11-24h2-disaster/957171?page=2)), and the DAC volume bug in 1.7. No Microsoft document describing a DAW-specific 25H2 regression was found. Pete Brown's (Microsoft) build guide: MMCSS threads are not affected by the foreground setting, Game Mode usually hurts a DAW, measure one change at a time ([Microsoft](https://devblogs.microsoft.com/windows-music-dev/?p=412)).

## 4. The CPU and file side for samples

- **Defender slows plug-in scans and sample loading.** Steinberg recommends excluding the VST2 and VST3 folders ([Steinberg](https://helpcenter.steinberg.de/hc/en-us/articles/18208450029330-Slow-VST-plug-in-scanning-on-Windows)); Native Instruments says to exclude library folders and to use NTFS, because exFAT "may result in significantly slower loading" ([NI](https://support.native-instruments.com/support/solutions/articles/69000879746-kontakt-slow-loading-times)). Microsoft: every exclusion lowers protection; use them sparingly ([Microsoft](https://learn.microsoft.com/en-us/defender-endpoint/configure-process-opened-file-exclusions-microsoft-defender-antivirus)).
- **Dev Drive** (ReFS, Windows 11) lets Defender scan after opening instead of before; Microsoft calls that safer than folder exclusions, but intends it for code and build output, and it needs a reformat ([Microsoft](https://learn.microsoft.com/windows/dev-drive/)). An advanced tip only.
- **For AudioLab:** never add exclusions silently. A button in Settings ("Speed up loading: ask Windows Defender to skip these folders") that runs elevated once, lists the folders, and explains the trade-off.
- **Streaming from disk:** overlapped unbuffered reads in 4 KB multiples ([Microsoft](https://learn.microsoft.com/windows/win32/fileio/file-buffering)); IoRing on Windows 11 as an optional fast path, checked at run time ([Microsoft](https://learn.microsoft.com/en-us/windows/win32/api/ioringapi/)). Never touch memory-mapped pages from the audio thread.
- **OneDrive:** on many Windows 11 PCs Documents is in OneDrive; "online-only" files download when opened, which blocks, and sync can lock files during autosave. Ableton tells users to mark project folders "Always keep on device" and to pause sync ([Ableton](https://help.ableton.com/hc/en-us/articles/360002855960)). AudioLab should check a file's cloud attributes (`FILE_ATTRIBUTE_RECALL_ON_DATA_ACCESS`) before streaming and warn, and suggest a project folder outside OneDrive.
- **Long paths:** 260 characters unless both a registry switch and the app's manifest allow more ([Microsoft](https://learn.microsoft.com/windows/win32/fileio/maximum-file-path-limitation)). The engine should use the `\\?\` form internally.

## 5. Plug-in hosting on Windows

### 5.1 Where plug-ins are

- **VST3:** `C:\Program Files\Common Files\VST3` (and `%LOCALAPPDATA%\Programs\Common\VST3`, mainly for developers), scanned recursively; a bundle is a folder `X.vst3\Contents\x86_64-win\X.vst3`; the old single-file form must still load ([locations](https://steinbergmedia.github.io/vst3_dev_portal/pages/Technical+Documentation/Locations+Format/Plugin+Locations.html); [format](https://steinbergmedia.github.io/vst3_dev_portal/pages/Technical+Documentation/Locations+Format/Plugin+Format.html)).
- **`moduleinfo.json`** in the bundle lists the plug-ins without loading the DLL ([Steinberg](https://steinbergmedia.github.io/vst3_dev_portal/pages/Technical+Documentation/VST+Module+Architecture/ModuleInfo-JSON.html)). It has no bus information, so a full scan is still needed once **(guess)**; JUCE had a bug making 0-channel descriptions from it ([JUCE forum](https://forum.juce.com/t/vst3pluginformatheadless-findalltypesforfile-creates-plugindescription-with-0-channels-if-moduleinfo-json-is-present/67867)).
- **CLAP:** `%COMMONPROGRAMFILES%\CLAP`, `%LOCALAPPDATA%\Programs\Common\CLAP`, and `CLAP_PATH`.
- **VST2:** no official folder; and Steinberg confirmed in 2020 that new hosts cannot license VST2 ([forum](https://forums.steinberg.net/t/can-i-create-vst-2-support-for-host-application-vst-3-license/202012)). The plan's P6a stands.

### 5.2 Crash isolation

- **Inside the engine with structured exception handling:** OpenMPT wraps every plug-in call in `__try/__except`, bypasses the faulting plug-in and marks the process as tainted ([OpenMPT](https://bugs.openmpt.org/view.php?id=1401)). Continuing after an access violation is not safe: the heap may already be damaged ([Raymond Chen](https://devblogs.microsoft.com/oldnewthing/20060927-00/?p=29563)). **Use it to catch, name the plug-in, write a crash dump, silence that plug-in, and ask the user to save and restart the engine**, not to carry on as if nothing happened. In route C the engine is already a separate process from the window, so the project survives anyway.
- **Out of process:** Bitwig offers within, together, by maker, by plug-in, individually ([Bitwig](https://bitwig.com/userguide/latest/vst_plug-in_handling_and_options)); REAPER native, separate, dedicated, and advises dedicated only for the troublesome ones ([reaper.blog](https://reaper.blog/2012/02/run-plugin-as-dedicated-process/)); FL Studio "make bridged", about 1 to 2 % CPU per plug-in ([Image-Line](https://www.image-line.com/fl-studio-learning/fl-studio-online-manual/html/plugins/wrapper.htm)). Cubase and Ableton have no sandbox.
- **The cost** (Ardour, an estimate, not a measurement): at 48 kHz and 64 frames, 384 plug-ins each alone mean hundreds of process switches per 1.3 ms block, 10 to 300 µs each in practice, so per-plug-in isolation needs buffers of 700 to 2,000 frames ([Ardour](https://ardour.org/plugins-in-process.html)). Users see Bitwig's sandbox cause spikes that vanish "within Bitwig" (forum).
- **Plan, unchanged from P5a and sharpened:** in the engine by default; "run apart" per plug-in, grouped in one helper process by default, with one wake per helper per block, never one per plug-in; shared memory for audio and events.
- **Plug-in windows from another process:** a cross-process child window links the two processes' input queues; a hang in one stalls the other ([Raymond Chen](https://devblogs.microsoft.com/oldnewthing/20130412-00/?p=4683)). For plug-ins that run apart, show the window as its own top-level window, owned by the helper, as REAPER does.

### 5.3 Windows-specific plug-in faults and the host's defence

| Fault | Defence |
|---|---|
| Plug-in changes FPU / MXCSR state | save and restore around every call, on audio and UI threads |
| Plug-in calls `CoInitialize` on our thread with another model ([Larry Osterman](https://learn.microsoft.com/en-us/archive/blogs/larryosterman/things-you-shouldnt-do-part-2-dlls-cant-ever-call-coinitialize-on-the-applications-thread)) | the UI thread is an STA set up with `OleInitialize` before any plug-in loads; no COM on audio threads |
| Copy protection (PACE/iLok) needs a window and a message pump while loading; a PACE bug once hung Cubase's scanner ([Steinberg forum](https://forums.steinberg.net/t/vst3-plugin-scan-hangs-on-new-ilok-protected-plugins/121872)) | the scanner process has a hidden window and pumps messages, with a time limit |
| `setActive` / `setProcessing` take seconds (Kontakt loading samples) | never on the audio thread, never while holding an engine lock |
| Crash on unload; JUCE kept every VST3 DLL loaded for years for this reason ([JUCE forum](https://forum.juce.com/t/unload-a-vst3/62639)) | never `FreeLibrary` at exit; unload during a session only after a delay |
| WebView2 plug-in windows that hang ([JUCE forum](https://forum.juce.com/t/br-webview-freezes-daw/64917)) | STA UI thread; a watchdog on the UI thread |
| `restartComponent` and `performEdit` called from the audio thread (old JUCE plug-ins did) ([JUCE forum](https://forum.juce.com/t/juce-incorrectly-calling-icomponenthandler-performedit-from-audio-thread/35040)) | accept the call on any thread, queue it, handle it on the UI thread ([Steinberg hosting FAQ](https://steinbergmedia.github.io/vst3_dev_portal/pages/FAQ/Hosting.html)) |
| 32-bit plug-ins | not supported (Cubase blocks them too) |

All of these apply on the Mac to some degree too; the floating-point rule and the "never on the audio thread" rules belong in the shared host code now.

### 5.4 High-DPI plug-in windows

- The app must be **Per-Monitor V2** aware. VST3 tells a plug-in its scale with `IPlugViewContentScaleSupport::setContentScaleFactor`, which exists for Windows exactly because the plug-in cannot find out by itself ([Steinberg](https://steinbergmedia.github.io/vst3_dev_portal/pages/Technical+Documentation/Change+History/3.6.6/IPlugViewContentScaleSupport.html)); CLAP has `set_scale`.
- For plug-ins that are not DPI-aware: create their parent window in mixed mode (`SetThreadDpiHostingBehavior(DPI_HOSTING_BEHAVIOR_MIXED)` and `SetThreadDpiAwarenessContext`) so Windows stretches them ([Microsoft](https://learn.microsoft.com/windows/win32/api/winuser/nf-winuser-setthreaddpihostingbehavior)). Ableton and FL Studio both have a per-plug-in "scale this window" switch ([Ableton](https://help.ableton.com/hc/en-us/articles/209775985-High-DPI-monitor-support); [Image-Line](https://www.image-line.com/fl-studio-learning/fl-studio-online-manual/html/plugins/wrapper.htm)). AudioLab should have the same.
- **A current trap:** JUCE 8.0.13 plug-ins drew about 1.56 times too big at 125 % in hosts that send a scale to a window that is already DPI-aware, and changed the host's DPI awareness ([JUCE forum](https://forum.juce.com/t/windows-dpi-scaling-broken-in-juce-8-0-13-for-some-daws-renoise/68923)). Hosts that rely on the system alone (REAPER, Cubase) were not affected. So: send the scale factor only when the plug-in is not per-monitor aware itself, set the thread's DPI context again before every plug-in window, and test with a JUCE 8 plug-in at 125 % and 150 %.

### 5.5 Scanning, and ARA

- Same design as on the Mac (child process, blocklist), plus: cache by path, size and date; read `moduleinfo.json` first; generous per-plug-in time limits (30 to 120 s for samplers) **(guess)**; tell the user about Defender if the first scan is slow.
- **ARA** (needed for Melodyne, which the user listed): the SDK is Apache 2.0 since 2021 ([Synthtopia](https://www.synthtopia.com/content/2021/05/13/celemony-releases-ara-sdk-under-open-source-license/)), fine for a closed app. Supported by Cubase, Studio One, REAPER, Logic, Pro Tools; not by Ableton or Bitwig ([Wikipedia](https://en.wikipedia.org/wiki/Audio_Random_Access)). It is the same work on both systems, so it belongs in the shared host, not in a Windows task.

## 6. The interface on Windows at 240 Hz

### 6.1 Electron today

- Chromium times frames on Windows by waiting for the vertical blank of the **primary** monitor (`MonitorFromWindow(nullptr, MONITOR_DEFAULTTOPRIMARY)` in [vsync_thread_win_dxgi.cc](https://chromium.googlesource.com/chromium/src/+/main/ui/gl/vsync_thread_win_dxgi.cc)), with a note that the interval is read from the window's monitor. **(guess)** On a 240 Hz screen that is not the primary one, animation may be tied to the primary screen's rate or paced unevenly. Users report this; the Chromium issues could not be read. Needs a check on the user's PC (task W15).
- A covered, minimised or locked window stops drawing and its JavaScript is throttled ([Chromium occlusion doc](https://chromium.googlesource.com/chromium/src/+/main/docs/windows_native_window_occlusion_tracking.md)). `backgroundThrottling: false` keeps the frames going ([Electron change](https://ayakael.net/mirrors/electron/commit/2190793fe6351e50940dec077907eaac1f16471c)). For AudioLab this is one more reason the sound must not depend on the page's timers: in the web engine the AudioWorklet is safe, but anything scheduled from the main thread (`setTimeout` transport logic) is not **(guess, to check in the code)**.
- `--disable-frame-rate-limit` / `--disable-gpu-vsync` make rAF run free; for measuring, not for shipping.
- Windows 11's "dynamic refresh rate" raises the rate only for listed apps on laptops ([Microsoft DirectX blog](https://devblogs.microsoft.com/directx/dynamic-refresh-rate/)); the user should set a fixed 240 Hz.

### 6.2 Native drawing later (stage 4, and before it)

- **Flip model** swap chains (`DXGI_SWAP_EFFECT_FLIP_DISCARD`), with the waitable-object flag for about one frame of latency; mixing GDI and Direct3D in one window falls back to the old copy model ([Microsoft](https://learn.microsoft.com/windows/win32/direct3ddxgi/for-best-performance--use-dxgi-flip-model)). DirectComposition stacks several swap chains with transforms and opacity, which fits the glass layers.
- **What others use:** Bitwig 5.2+ draws with **Skia** on Direct3D, Vulkan or OpenGL ([Bitwig](https://bitwig.com/support/technical_support/the-bitwig-studio-window-is-not-displayed-correctly-after-updating-to-version-52-on-windows-66)); Ableton 12.2 added an optional GPU renderer on Windows ([Ableton](https://help.ableton.com/hc/articles/4405388230674)); REAPER draws mostly on the CPU with its own LICE library ([Cockos WDL](https://www.cockos.com/wdl)); JUCE 8 has a Direct2D renderer ([KVR](https://www.kvraudio.com/news/juce-8-now-available-61009)).
- **For AudioLab's stage 4:** Skia (Graphite or Ganesh: Metal on the Mac, Direct3D on Windows) is the one choice that draws the same glass on both systems from one code base and is proven in a DAW. A Mac-only AppKit and Metal interface (as the Mac plan says) would mean writing the Windows interface again. **This is the biggest Windows-driven change to the plan (section 12).**
- **A middle step that helps now (guess):** the meters, waveforms and spectrum, which are what needs 240 Hz most, can be drawn by the engine into native child windows with their own flip-model swap chains while Electron keeps the rest. That also escapes the primary-monitor timing. Worth a prototype after the engine is in the app (task W16).

## 7. Installers, signing, updates

- **NSIS stays.** MSIX cannot write to the install folder or to `Common Files\VST3`, redirects AppData and registry, and allows no drivers ([Microsoft](https://learn.microsoft.com/windows/msix/desktop/desktop-to-uwp-prepare)); electron-updater cannot update an MSIX ([electron-builder](https://www.electron.build/docs/appx)). The Microsoft Store also takes a signed `.exe` as a Win32 listing, with no SmartScreen warning for Store users, if the app updates itself ([Microsoft](https://learn.microsoft.com/en-us/windows/apps/distribute-through-store/how-to-distribute-your-win32-app-through-microsoft-store)).
- **Signing:** Azure **Artifact Signing** (renamed from Trusted Signing, "no functional difference"): US$9.99 a month for 5,000 signatures; a paid Azure subscription; **individual developers only in the US or Canada**; organisations in the US, Canada, EU, UK, Australia, New Zealand, Japan, South Korea, Singapore, Switzerland, Norway and Israel ([pricing](https://azure.microsoft.com/en-us/pricing/details/trusted-signing/); [quickstart](https://learn.microsoft.com/azure/artifact-signing/quickstart)). electron-builder v26 signs with it through `win.azureSignOptions` ([electron-builder](https://www.electron.build/v26/docs/features/code-signing/code-signing-win)); the app uses 25.x, so check or upgrade.
- **Other certificates:** since June 2023 keys must live in hardware or a cloud HSM, and from 1 March 2026 certificates last at most 460 days ([CA/B Forum CSC-31](https://cabforum.org/2025/11/17/ballot-csc-31-maximum-validity-reduction)). An ordinary OV certificate from a CA is the route if Azure is not open to the user (cost not checked; usually a few hundred US$ a year **(guess)**). Certum's €49 certificate is for open-source projects only ([Certum](https://shop.certum.eu/open-source-code-signing-on-simplysign.html)).
- **SmartScreen:** an unsigned download shows "Windows protected your PC"; a signed but new one shows "unrecognized app" with the publisher's name; reputation takes weeks and hundreds of clean installs; EV certificates no longer skip this; unsigned apps lose reputation with every update; Smart App Control blocks unsigned apps without reputation ([Microsoft](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation)).
- **Updates:** electron-updater checks the publisher of a signed update with `Get-AuthenticodeSignature`; unsigned, it trusts only the SHA-512 in `latest.yml` ([electron-builder](https://www.electron.build/docs/features/auto-update)). Differential updates through `.blockmap` files already work with NSIS.
- **Updating the engine helper:** versioned folders (`engine\1.4.2\`), install beside the running one, switch at the next stop or restart, ask the engine to stop cleanly first, check locked files with the Restart Manager (`RmGetList`), and version the engine's protocol so a new interface refuses an old engine **(guess, standard practice)**. Velopack is a modern updater with C++ bindings if the app later leaves Electron ([Velopack](https://docs.rs/crate/velopack/1.1.1/source/README.md)).
- **Note found while reading `desktop/package.json`:** the `publish` block still names the repository `Audio-Lab-Beta`. It works through GitHub's redirect; worth changing to `Audio-Lab-Pro-Alpha` in a desktop task (not done here, `desktop/` is out of scope).

- **Desktop session:** yes, the job runs in a logged-on session; screenshots of windows work ([example](https://gist.github.com/WestonThayer/f8b72c8e1866585b94daa1a94e822ecc)). Fixed resolution, one monitor, 100 % scale **(guess)**: high-DPI tests need a forced scale or have to wait for the user.
- **Sound:** no audio device. Mozilla's cubeb CI installs **VB-CABLE** with `devcon` and restarts the audio services ([setup_sound.ps1](https://raw.githubusercontent.com/LABSN/sound-ci-helpers/master/windows/setup_sound.ps1); [cubeb workflow](https://kdab.searchfox.org/firefox-main/source/third_party/rust/cubeb-sys/libcubeb/.github/workflows/build.yml)). VB-CABLE is donationware and needs a paid licence "in a professional context" ([VB-Audio](https://vb-audio.com/Services/licensing.htm)): small, but the user should decide. The Scream driver (MS-PL) needs test mode on Windows 11 and will not install on a hosted runner **(guess)**.
- **ASIO on CI:** no ASIO driver exists on the runner; FlexASIO (MIT) on top of VB-CABLE gives a real ASIO driver to test the loader against **(guess, to try)**. ASIO builds on CI need the SDK fetched at build time and the licence agreement signed before any release.
- **Plug-ins on CI:** Surge XT has a Windows installerless zip ([Surge](https://surge-synthesizer.github.io/downloads)); Steinberg's validator and example plug-ins build from the SDK ([classmethod](https://dev.classmethod.jp/en/articles/vst3-ci-using-validator-on-github-actions/)); pluginval (GPLv3, run as a separate tool) ([pluginval](https://raw.githubusercontent.com/Tracktion/pluginval/develop/README.md)).

## 10. UI and product ideas that came out of the research

- **"Output mode" with three plain choices on Windows:** *Shared* (other apps can play, Windows mixes), *Exclusive / bit-perfect* (AudioLab owns the DAC, the DAC follows the project's rate), *ASIO* (the interface maker's driver, lowest latency). One sentence under each, and a light that says what the path does right now (the Roon-style signal path already planned in `settings-research-audiophile.md`).
- **Device profiles that remember per device:** mode, rate policy (follow the project / fixed), buffer, measured latency, volume mode (hardware, software, none), safe level. Plugging the Gryphon back restores its profile on either system.
- **A "Volume" readout that says where the volume is done:** "on the DAC", "in Windows, before the DAC", "on the unit's knob (the computer cannot set it)". Same words on both systems.
- **A "System check" page** (N-W6) with a traffic light and advice; a "Copy report" button like the test app's.
- **A clear message for every refusal:** "Another app is using the Gryphon exclusively", "Exclusive use is turned off for this device in Windows Sound settings (open it)", "The ASIO driver asked to restart; restarting audio…".
- **Per-plug-in window switch "Scale this window"** and "Run apart"; a plug-in that crashed shows a card in its place with "Reload", as Bitwig does.
- **"Speed up loading"**: the Defender button, the OneDrive warning, and a slow-scan hint.
- **Background mode**: an option "keep full speed when AudioLab is in the background" (on by default for a DAW), which is the power-throttling opt-out made visible.

## 11. Proposed new tasks

Each is one cloud task of 1 to 3 hours. "CI" means a GitHub `windows-latest` runner unless named otherwise. None touches `index.html` unless it says so; most add to `native/` and a new workflow `.github/workflows/native-win.yml`.

**W0. The ASIO agreement (the user, about 15 minutes).** Download the ASIO SDK from steinberg.net, read the agreement PDF, sign as "Individual Developer" (or the company), email it to `sdklicenseagreements@steinberg.de`. Note the date in `docs/native-mac-picks.md` or a new picks line. Proof: the countersigned PDF. Nothing with ASIO is released before it.

**W1. Windows CI and the engine builds on Windows.** Make `native/` build with MSVC (VS 2026) and with clang-cl on `windows-latest`; the Bitcrusher test (test A) runs and compares bit for bit with the web reference; `-ffp-contract=off` equivalent (`/fp:precise`, no FMA contraction) checked. Proof: CI, 144,000 of 144,000 samples identical on Windows x64. User: nothing.

**W2. Windows device probe (read only), like test A's device list.** A small program `alprobe.exe`: every endpoint with name, id, form factor, shared format (`PKEY_AudioEngine_DeviceFormat`), mix format, device period (default, minimum), IAudioClient3 periods, exclusive formats accepted (probe list), hardware volume / mute / meter, dB range, ASIO drivers listed from the registry (names only, no SDK needed). Proof: runs on CI with VB-CABLE installed (if the user approves its licence) and lists it. User: runs it on their PC with the Gryphon and the Zoom (with and without the Zoom driver) and pastes the report.

**W3. WASAPI exclusive output in `alengine`.** Event-driven exclusive with the alignment retry, format probe, rate switching, integer output (`sample_convert.h` already exists), same JSON commands as the Mac (`devices`, `open`, `volume`, `status`). Proof: on CI through VB-CABLE: open exclusive, play the web engine's renders, record from the cable, compare samples (VB-CABLE is float in shared mode; exclusive formats as available). User: plays through the Gryphon at 44.1, 96 and 192 kHz and confirms the DAC's display shows the rate.

**W4. Endpoint volume and device changes on Windows.** `IAudioEndpointVolume` get, set, callback; `IMMNotificationClient`; device-lost recovery (same id, then default); read volume back after return and after resume, with the safe-level rule. Proof: CI changes the volume from a second process and sees the event; disables and enables the virtual device and sees the move and return. User: moves the Windows volume slider and sees AudioLab follow, unplugs the Gryphon.

**W5. WASAPI shared and low-latency shared output.** IAudioClient3 where offered, plain shared otherwise, `RAW` stream option where offered, our resampler when the rate differs (needs the N2 resampler). Proof: CI plays and records through the cable; reports the periods offered. User: built-in speakers and a Bluetooth headset.

**W6. Real-time setup on Windows.** MMCSS Pro Audio with a switch, power-throttling and timer opt-out for process and audio threads, CPU Sets to the highest efficiency class, MXCSR on every audio thread, locked buffers. Proof: CI prints the thread's priority, the CPU set, the throttling state read back, MXCSR bits. User: plays at 64 frames with AudioLab covered by another window for five minutes; the report counts late callbacks.

**W7. System check, step 1 (engine side).** Per-callback lateness, cycles against wall time, page faults, core and efficiency class, counted and summarised; power plan, USB selective suspend, Efficiency mode read out. Proof: CI with an artificial stall (a thread that hogs a core) shows the lateness rise. User: report from their PC.

**W8. ASIO loader without the SDK files (listing only).** Read `HKLM\SOFTWARE\ASIO`, show names and DLL paths, mark 32-bit-only drivers. Allowed before W0 returns, as it does not talk to the driver **(guess: Steinberg's FAQ wording is broad; if in doubt wait for W0)**. Proof: CI with FlexASIO installed shows it. User: list shows Zoom and iFi drivers if installed.

**W9. ASIO host (after W0 is countersigned).** SDK fetched at build time from Steinberg, never committed; open, buffer sizes, rates, `bufferSwitchTimeInfo`, `ASIOOutputReady`, messages to a control thread with time limits, latencies, the driver's panel. Proof: CI against FlexASIO on VB-CABLE plays and records sample-exact. User: the Zoom AMS-24 through Zoom's driver at 64 and 32 frames; iFi's driver with the Gryphon.

**W10. Latency measurement.** A ping out, back through a cable (or the AMS-24's own LOOPBACK switch, which the manual mentions), find the delay to the sample, store it per device, rate and buffer. Proof: CI through VB-CABLE (a known delay). User: a cable on the Zoom, or its loopback switch.

**W11. VST3 host on Windows.** The existing `native/host` on Windows: folders, bundle and single-file forms, `moduleinfo.json`, scanner child process with a hidden window and message pump and time limit, SEH catch-and-report around every plug-in call, FPU save and restore, STA UI thread. Proof: CI with Surge XT (Windows zip) and the SDK examples: the same table as test B (load, state, export, 96 kHz and 32 frames), one example made to crash on purpose, Steinberg's validator run. User: their Windows plug-ins (if they have a Windows PC with plug-ins; question below).

**W12. Windows test app.** The Mac test app's twin as a small Win32 or Dear ImGui program: device list, output mode (shared, exclusive, ASIO when W9 is in), rate, buffer, volume, plug-in list, load, open window, play pattern, report. Proof: CI starts it, opens Surge XT's window and takes a screenshot. User: the same steps as on the Mac, and pastes the report.

**W13. Plug-in windows and DPI.** Per-Monitor V2 app, mixed DPI hosting for unaware plug-ins, `setContentScaleFactor` only when the plug-in is not aware, a per-plug-in "Scale this window", resize both ways, move between monitors. Proof: CI at a forced 150 % scale (registry and re-login on the runner, if possible; else only 100 %) with Surge XT and a JUCE 8 plug-in. User: two monitors with different scale.

**W14. Defender, OneDrive and file checks.** Detect Defender real-time protection and whether plug-in and library folders are excluded (read only, `Get-MpPreference` needs admin to read exclusions **(guess)**: else time a test scan), cloud placeholder check, long-path handling, the "Speed up loading" button that runs elevated once. Proof: CI creates a placeholder-like file with the attributes and sees the warning. User: clicks the button once.

**W15. 240 Hz check in the Electron app on Windows (desktop task, touches `desktop/` only).** A hidden diagnostics page: rAF rate and frame-time histogram per monitor, which monitor Chromium paces to, with `backgroundThrottling` on and off. Proof: CI runs it (60 Hz virtual screen). User: runs it with the 240 Hz screen as primary and as secondary and pastes the numbers.

**W16. Native meter window prototype.** The engine draws one meter and one scrolling waveform into a child window with a flip-model swap chain (Direct3D 11), placed over the Electron window. Proof: CI screenshot, frame timing from the swap chain statistics. User: does it look smooth at 240 Hz next to the web meters.

**W17. Signing in CI (after the user has a signing account).** Azure Artifact Signing or an OV certificate in electron-builder (upgrade to v26 if needed), `publisherName`, sign `alengine.exe` and helpers too, check the signature in CI. ## 12. What the native plan should change for Windows

1. **Send the ASIO agreement now, not when Windows starts.** The wait (weeks to months) is the longest lead time in the Windows plan. It costs nothing.
2. **The device layer is two paths on Windows.** Plan WASAPI (exclusive and shared) as the first Windows output, because it needs no licence, reaches every device and gives bit-perfect output to the DAC. ASIO second.
3. **Keep the engine's device interface format-neutral now.** `coreaudio.cpp` is Mac only, which is right, but the commands of `alengine` (`devices`, `formats`, `open`, `volume`, events) should be written down as the contract for both systems, with fields that exist on Windows: "volume kind: hardware / software / none", "mode: shared / exclusive / asio", "refusal reason". Cheap now, expensive later.
4. **Real-time rules in the shared code from stage 3:** two-path engine (live set and render-ahead), a small fixed number of real-time threads (≤ the P-cores, and ≤ 28 on Windows for MMCSS), floating-point state saved around plug-ins, no lock held during `setActive`. These are the same on the Mac and avoid a Windows rewrite.
5. **The drift resampler of N2 is also the multi-device answer on Windows.** Build it once, for both.
6. **Plug-in host rules for Windows go into the shared host now:** FPU save and restore, `restartComponent`/`performEdit` accepted from any thread, never unload at exit, scanner with a message pump. The Mac benefits as well.
7. **Stage 4 (native screens): choose a toolkit that also runs on Windows.** An AppKit-and-Metal interface would have to be written a second time for Windows. Skia (Metal and Direct3D) is the proven cross-platform choice for a DAW (Bitwig). This is a change in the plan's stated direction ("AppKit with Metal"); question R2 should be asked again with this in mind.
8. **"Run apart" must be grouped by default** (one helper for all apart plug-ins, or per maker), with one wake per helper per block. Per-plug-in processes only for troublemakers.
9. **Windows CI from the first Windows task**, with a virtual audio device, so every Windows step is proven by machines before the user tests it, as on the Mac.
10. **Windows can start earlier for the read-only parts.** R5b put Windows after stage 3. The tasks that only read (W1, W2, W8, W15) and the signing (E1, W17) do not compete with the Mac engine and answer questions early. Suggested: allow them now; keep the Windows output and hosting after stage 3 as picked.
