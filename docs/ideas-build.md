## 1. Rules every step keeps

- **Lanes.** Four index.html tasks run at once: lane A (main window, glass, devices: GS4, MD1, SC, DV), lane B (Settings window and audio devices: ST), lane C (task FT, the 40 picked features and MIDI controllers, `docs/features-build.md`), lane D (this plan). Edits are small Python scripts with unique asserted anchors, kept in `tools/feature-lab/ni/`, so a rebase re-runs them on the fresh file. `git pull --rebase` before every commit and push; on a conflict, rebase and re-run the edit script on the fresh file, never merge by hand. VERSION is the highest on main + 0.001 at push time, re-checked after a rebase; UI tests run again after a rebase. Other lanes' wip commits are not a reason to stop.
- **Where code goes.** One block per idea with the name prefix `NI_` (globals, functions) and `ni` (CSS classes, ids, data attributes). New JS before `function askChoice(title,text,btns,icon){`; new CSS before `.dacv{display:flex;`. Shared lane D pieces live in one object `NI` (for example `NI.an` the analysis cache, `NI.tape` the control tape) so later steps find them.
- **Commands and settings.** Every new action is an entry in `SCA` with a namespaced id (`ni.clipExplain`, `ni.freqMap`, `ni.clashes`...) so task DL2 adopts them into the commands registry unchanged (`docs/extensions-plan.md` 9.6). Every new setting is one row in the shape of the S4 settings table (`docs/settings-round-1.md`: id, label, page, block, scope, default, help line, search words), collected in one list `NI_SETTINGS` until S4 lands.
- **Hooks for other lanes.** If an idea needs the Settings window (lane B) or a device frame lane A is rebuilding right now, the logic and an in-place UI ship now, and a small named hook `NI_HOOKS.<name>` is left for the other lane; each hook is listed in the step's log entry and in section 6.
- **Nothing breaks.** Old projects load: new project fields are optional, under one versioned key per idea (`S.ni_arc={v:1,...}`, `S.ni_tree={v:1,...}`), ignored when missing, never required. Every existing feature works as before. The audio path of existing devices does not change: exports stay bit-identical, and the Fractals levels are checked every run with `tools/engine-tests/export_same.py` against the newest reference numbers in `docs/backlog-log.md` (today, from task AB2, v0.229: solo Kick -19.05560 dB, Bass -35.48685 dB, beats 64 to 96, master at -10 dB; -9.75669 and -25.48699 dB at 0 dB). The log says which numbers were measured.
- **Analysis never touches the audio thread.** Every measurement in this plan is done on offline renders (`renderMixChunked` with `only` per track) or on data already computed for the meters, in a worker or in idle slices of the main thread, cached, and cancelled when the project changes. Nothing new runs in an AudioWorklet. Monitor-only additions (I15 lenses) sit after the master and are bypassed for export.
- **Look and feel.** Today's look, Inter 11/12/13/15, glass from the engine (no `backdrop-filter`), dark and Light. Anything that measures sound follows the instrument look of `docs/design-round-4-instruments.md` (graticule, units on every read-out, one channel colour per track repeated on trace and label, perceptual colour maps such as magma or viridis, no red against green; the user's DR4 picks win once they are in) and the science philosophy of `docs/glass-engine-plan.md` section 1: "smart and sciencey, clear, intuitive, snappy". Tooltips on every new control, plain language, no em dashes in UI text. Snappy: nothing per frame while idle; views draw on change or while playing, and only when visible.
- **The Assistant.** Anything that uses it says honestly what needs a model connection and what works offline. Nothing the user did not accept goes into the song: proposals are previews until the user clicks Keep, and Keep is one undo step.
- **Tests.** `tools/ui-tests/taskNI_<step>.py`, headless, with the checks section 5 of the research lists for that idea, screenshots of anything visible looked at (dark and Light), the existing UI tests pass, no console errors.
- **What only the user can judge** (ears, taste, the feel on the real Mac) is written plainly in the log and the notification, with what to try.

## 2. What exists today (v0.229, read for this plan)

- **Offline render:** `renderMixChunked(sr,b0,b1,tail,lim,only,prog,fastMode)` renders any beat range of the whole mix or of one track (`only`), in chunks. This is the base of every analysis in lane D.
- **Meters:** `meters()`, `trackMeters()`, `peakOf()`, `mtrPeak()`; mixer strips and master show peaks. There is no clip event log yet; I3 adds one (it only reads values the meters already have).
- **Undo:** whole-project snapshots (`pushUndo()` pushes `undoSnap()`, 80 deep; `undo()` restores). I23 works on the differences between neighbouring snapshots.
- **Time Machine:** versions in IndexedDB (`tmSnap`, `tmList`, `tmLoad`, `tmRestore`), a version tree window (`tmOpenWin`), crash recovery. I22 and I23 build on it.
- **Mix A/B:** `mabCapture()` and its pair; I14 builds on it.
- **Cables:** the cable lane (`cabList`, `cabDraw`, `cabPop`, `cabLegend`); I12 draws in it with its own colour behind a switch.
- **Mono check** (`UI.monoChk`, sum in the master), safety limiter, DC blocker, headphone ceiling; I4 and I16 sit next to them.
- **Scales and key:** `SCALES`, the piano roll's scale lock and root. Lane C's FT-F11 adds a project key; lane D reads it when it is there and falls back to the scale lock.
- **Sections** (`S.sections`: name, start, length, colour), tempo map (`tmapSegs`), signatures.
- **Assistant:** `AI` with tools (`aiTrack`, `aiPutClip`, `aiPush` makes one undo step per turn). Capture (notes played without recording), audio to MIDI, stem splitter, Tuner, Ducker, 1,238 presets.
- **Workers:** blob workers are already used (`SCLKW` clock, `WARPQ.w` warp), so an analysis worker follows the same pattern.
